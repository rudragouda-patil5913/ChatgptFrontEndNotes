### Lexical Environment

A Lexical Environment is a data structure created for every scope. It stores the bindings declared in that scope and a reference to its outer (parent) lexical environment. This allows JavaScript to perform identifier resolution through the scope chain.

### A Lexical Environment is not the Scope Chain.

It's one object.

### Scope Chain

Is the linked sequence of Lexical Environments.

```
Lexical Environment = one node
Scope Chain = all the connected nodes
```
 
### Closures
 
"A closure is a function bundled together with its lexical environment."

A closure is possible because:

- The function object remembers the Lexical Environment in which it was created.
- That reference keeps the Lexical Environment alive even after the Function Execution Context is gone.
- Therefore, the function can still access those bindings later.

### let for loop

- The ECMAScript specification defines that a for loop with let creates a fresh lexical binding for each iteration.
- Closures simply make that behavior visible because each callback retains a reference to its own binding.

A closure is meaningful when the returned function actually uses bindings from its outer lexical environment.

### Why does a closure keep variables alive after a function returns?

When a function returns another function, the returned function maintains a reference to the outer function's Lexical Environment through its Outer Lexical Environment Reference. As long as that returned function remains reachable, the Lexical Environment containing the required bindings is also reachable, so the garbage collector cannot reclaim it.

## Memory leaks

Imagine someone writes:

```
function loadData() {
const hugeArray = new Array(1000000).fill("Data");

    document.getElementById("btn").onclick = function () {
        console.log(hugeArray.length);
    };

}
```

At first glance, it looks harmless.
But imagine:

- loadData() is called 100 times.
- Each call creates a new hugeArray.
- Each click handler closes over its own hugeArray.
- None of the event listeners are removed.

#### What happens?

- You now have 100 huge arrays still reachable through event listeners.
- The browser cannot garbage collect them.
- Memory usage keeps increasing.

#### This is a classic memory leak caused by closures.

## How Do We Fix It?

When the listener is no longer needed:

```
button.removeEventListener("click", handler);
handler = null;
```

Now:

- The event listener is removed.
- The function becomes unreachable (assuming no other references).
- The closure becomes unreachable.
- The garbage collector can reclaim the memory.

## React Connection

#### This is exactly why React developers write cleanup functions.

```
useEffect(() => {
function handleResize() {
console.log(window.innerWidth);
}

    window.addEventListener("resize", handleResize);

    return () => {
        window.removeEventListener("resize", handleResize);
    };

}, []);
```

#### Why do we remove the listener?

- Not just to stop handling resize events.
- It's also to allow the function and anything it closes over to become unreachable when the - component unmounts, preventing memory leaks.
- This is one of those moments where your JavaScript fundamentals directly explain a React best practice

## "Do closures cause memory leaks?"

No. Closures are a JavaScript language feature. A closure only causes a memory leak if it unintentionally keeps references to objects that are no longer needed, preventing the garbage collector from reclaiming them.

A closure retaining memory is not a memory leak. A memory leak occurs when memory remains reachable even though the application no longer needs it.

### Advantages of Closure

- Data Encapsulation
- Module pattern

```
function Counter() {
let count = 0;

    return {
        increment() {
            count++;
        },

        decrement() {
            count--;
        },

        value() {
            return count;
        }
    };

}
```

Outside code cannot do:
counter.count = 100;
because there is no count property on the returned object.
The only way to change it is through the exposed methods.
This pattern is called the Module Pattern

### How were private variables implemented before JavaScript classes introduced #private fields?

Before #private fields, JavaScript developers used closures. A function created a Lexical Environment containing private bindings and returned an object exposing only selected methods. Those methods formed closures over the Lexical Environment, allowing controlled access to the private state while preventing direct access from outside the function.

### Why don't circular references cause memory leaks in modern JavaScript?

Modern JavaScript engines use a reachability-based garbage collection algorithm (Mark-and-Sweep). Circular references alone do not prevent garbage collection. If a group of objects is no longer reachable from any garbage collection root, the entire group becomes eligible for garbage collection, even if the objects reference each other.
