### Why use Exponential Backoff instead of immediate retries?

Immediate retries can overwhelm an already struggling server, creating a retry storm. Exponential backoff spaces out retries, giving the server time to recover. In production systems, exponential backoff is often combined with jitter to prevent many clients from retrying at exactly the same time.

### Should every API use exponential backoff?

No. I would only use exponential backoff for transient failures where retrying has a reasonable chance of succeeding, such as network issues or 5xx server errors. I would avoid retrying client-side errors like 400, 401, 403, or 404 because retrying won't fix an invalid request, authentication problem, permission issue, or missing resource. I would also be careful with non-idempotent operations like payment APIs, where retries could cause duplicate operations unless the backend supports idempotency.

### "Would you retry a payment API?"

Only if the API is designed to be idempotent. Otherwise, retrying could result in duplicate payments. Payment systems usually solve this using idempotency keys so that multiple retries are treated as the same request.

### When would you use AbortController?

I use AbortController to cancel unnecessary or obsolete network requests. Common examples include search autocomplete, page navigation, component unmounting in React, and preventing stale API responses. It improves performance and avoids race conditions caused by outdated responses.

Debounce
↓
Prevents unnecessary requests.

AbortController
↓
Cancels requests that are already running.

They solve different problems.

### If you're already using Debounce, do you still need AbortController?

Yes. Debounce reduces the number of requests sent, but once a request has already started, Debounce cannot stop it. AbortController is used to cancel in-flight requests that are no longer needed. In many search implementations, both are used together.

### Should every API request use AbortController?

No, I wouldn't use AbortController for every request. I would use it only when older requests become irrelevant. Search autocomplete is a perfect example because users continuously change their input, making previous requests obsolete. However, for critical operations like payments, order placement, or profile updates, I generally would not cancel the request once it has been sent, because those operations modify server state and should complete reliably.

I decide whether to use AbortController based on the business operation rather than the API itself. If the request becomes irrelevant to the user, like search suggestions or product filtering, I cancel it. If the request represents a critical business transaction, such as a payment or placing an order, I generally allow it to complete because cancelling it could leave the system in an inconsistent state or create a poor user experience.

### what is EventEmitter?

EventEmitter is an object that allows different parts of an application to communicate using events. One part emits an event, and other parts that subscribed to that event are notified.

EventEmitter is a design pattern used to implement event-driven communication. It allows different parts of an application to subscribe to events and react when those events are emitted, reducing direct coupling between modules.


### Difference between EventEmitter and Pub/Sub?
EventEmitter is typically used for communication within the same application where an emitter directly manages its listeners. Pub/Sub introduces a broker between publishers and subscribers, allowing them to remain completely independent. This makes Pub/Sub more scalable and suitable for distributed systems.
