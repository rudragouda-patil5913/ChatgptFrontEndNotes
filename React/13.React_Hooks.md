### What does useState do?

useState allows React to preserve data across renders and schedule a new render when that data changes. State behaves as a snapshot for each render, so calling the setter doesn't mutate the current state variable immediately. When the next state depends on the previous state, I prefer functional updates, and for objects or arrays I treat state immutably by creating new references.

function Counter() {
const [count, setCount] = useState(0);

function handleClick() {
setCount(count + 1);
setCount(prev => prev + 1);
setCount(count + 1);
}

console.log(count);

return <button onClick={handleClick}>+</button>;
}

The answer is 1. This one is tricky, so it's worth understanding.
The current render has:
count = 0

React queues these updates in order:
setCount(count + 1); // replace with 1
setCount(prev => prev + 1); // 1 → 2
setCount(count + 1); // replace with 1 again

### Why does useEffect exist?

useEffect allows a React component to synchronize with systems outside React's rendering process, such as network connections, timers, browser APIs, subscriptions, or third-party libraries. React performs rendering as a pure calculation, then Effects run after the UI has been committed. When dependencies change, React cleans up the previous synchronization before establishing the new one.

useEffect lets a component synchronize with an external system after React commits the UI.

```
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    document.title = `Count: ${count}`;
  }, [count]);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
}
```

### Am I synchronizing with something outside React?

If yes use useEffect hook.

### Cleanup with AbortController

```
useEffect(() => {
  const controller = new AbortController();

  async function loadUser() {
    try {
      const response = await fetch(
        `/api/users/${userId}`,
        { signal: controller.signal }
      );

      const data = await response.json();

      setUser(data);
    } catch (error) {
      if (error.name !== "AbortError") {
        console.error(error);
      }
    }
  }

  loadUser();

  return () => {
    controller.abort();
  };
}, [userId]);
```

### Does cleanup only run on unmount?

❌ No.
It also runs before an Effect re-synchronizes because its dependencies changed.

### The 4-question useEffect checklist

Before writing an Effect, ask:

1. What external system am I synchronizing with?
2. Which reactive values does that synchronization depend on?
3. What cleanup reverses the setup?
4. Could this instead be calculated during render or handled by an event?

### What is useRef and when would you use it?

useRef provides a mutable container that persists across renders without causing a re-render when its value changes. I use it for values that need to survive renders but don't directly affect the UI, such as timer IDs or external instances, and for accessing DOM elements when imperative browser operations like focus or scrolling are necessary.

Refs are commonly useful for:

- Focus
- Scrolling
- Measuring DOM elements
- Video playback
- Canvas
- Third-party DOM libraries

### Lifting State Up

Move shared state to the nearest common ancestor of the components that need it.

### What is Lifting State Up?

Lifting state up means moving shared state to the nearest common ancestor of the components that need it. That parent becomes the single source of truth and passes data and update callbacks down through props, keeping sibling components synchronized while preserving React's one-way data flow.

### Should we lift state as high as possible?

No. State should be kept as local as possible and lifted only as high as necessary. Keeping state close to where it's used improves ownership, maintainability, and can avoid unnecessary rendering across unrelated parts of the application.

### Why does Context API exist?

Context allows a value to be made available to a component subtree without manually passing it through every intermediate component. I use it for genuinely shared concerns such as authentication, theme, or locale. I don't treat Context as a replacement for all props or local state because excessive Context usage can hide dependencies and create broader re-render patterns.

### Why combine Context with useReducer?

useReducer centralizes complex state-transition logic, while Context makes that state and its actions available to distant components without prop drilling. Combining them can be a clean solution for moderately complex shared state without introducing an external state-management library.

### When should state be global?

I don't make state global simply because multiple components use it. I first keep state local and lift it to the nearest common owner when necessary. Context works well for values shared across a subtree, while an external store becomes useful when shared client state grows complex or requires granular subscriptions and stronger tooling. I also distinguish client state from server state because API data often benefits more from a dedicated caching/query solution.

### Why does Redux exist if Context exists?

Because they solve different layers of the problem.
Context:
How do I make a value available throughout part of my React tree?

Redux:
How do I organize, update, subscribe to, and debug complex shared application state?

Redux provides an external store with structured state updates and an ecosystem around it.
Modern React applications generally use:
Redux Toolkit
rather than writing old-style Redux boilerplate manually.

### Context vs Redux?

Context is primarily a mechanism for making values available across a React subtree without prop drilling. Redux Toolkit is an external state-management solution that provides structured state transitions, selective subscriptions, middleware, DevTools, and conventions useful for complex shared client state. I wouldn't choose between them based purely on application size; I'd choose based on the state ownership, update frequency, complexity, and tooling requirements.

### Redux vs Zustand?

Both provide external shared state. Redux Toolkit offers stronger conventions, mature tooling and an extensive ecosystem, which can be valuable for complex applications and larger teams. Zustand provides a much smaller API with less ceremony and straightforward selective subscriptions. The choice depends more on architectural and team requirements than on one being universally better.
